# Polyamory & Family Structures

A story-agnostic reference toolkit for writing multi-partner relationships and the households they form — independent of any swap/change mechanics (a story can use this with or without the `change-worldbuilding-toolkit` skill).

## What This Skill Covers

The skill is organized into aspects, each covering one facet of building a multi-partner family structure in fiction. Not every aspect exists yet — this is a living toolkit that grows one pass at a time.

### Built
- **Household Agreements & Norms** (`references/household-agreements.md`) — a checklist of the categories a multi-partner or blended household typically needs to have decided: sleeping arrangements, decision-making systems, communication norms, property/finances, chores, conflict resolution, guest and pet policy, family traditions, and how the household handles major changes (new members, births, someone leaving).
- **Integrating New Members & Inviting Others In** (`references/integration-and-intimacy.md`) — a household's philosophy and process for inviting others into their intimate life, from a single shared night through to genuine lasting membership; the consent standard that applies every time, with particular care where a staff or power-differential relationship is involved.

### Planned (not yet built — flag to the user if one of these would help and ask before drafting)
- **Legal & Institutional Structures** — how the story's world treats multi-partner relationships legally: marriage law limitations, formal vs. informal recognition, custody/parentage across multiple adults, inheritance, insurance/next-of-kin questions, name changes.
- **Terminology & Relationship-Structure Vocabulary** — shared vocabulary for naming a structure precisely (hierarchical vs. non-hierarchical, polyfidelity, kitchen-table vs. parallel polyamory, etc.), the same role the swap toolkit's Mental Trait Taxonomy plays for personality traits.

## Workflow

1. **A story introduces a multi-partner household:** read `references/household-agreements.md` and use it as a prompt list — identify which categories that story's own document should address, then have the story define the actual content. This file is a checklist of *what needs deciding*, not pre-written answers.
2. **A story needs something from a planned-but-not-built aspect** (legal recognition, how a member joined, precise relationship-structure terminology): don't invent it ad hoc — flag to the user that this aspect isn't built yet and ask whether to draft it now as a new pass, same as any other toolkit expansion.
3. **Names/roles in the reference file are generic** ("incoming member," "household children") — always substitute the story's actual cast when applying a category, never leave placeholder language in the story's own document.
