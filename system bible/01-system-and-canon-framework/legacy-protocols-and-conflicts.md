# Reusable Rules Recovered from Legacy Protocols

Status: REUSABLE DESIGN REFERENCE
Authority: SUBORDINATE TO CURRENT PROJECT GOVERNANCE

The legacy protocol sources contain experiments, transcripts, and specialized story configurations. Their characters, plots, settings, and individual events are not imported into the System Bible. This file preserves only reusable design rules and failure lessons.

## Imported authority is scoped

A recovered file may call itself a system instruction, master protocol, absolute law, or single source of truth. Those labels describe its intended authority in its original context. They do not grant project-wide authority after import.

Before reusing any recovered protocol:

1. identify the domain it governed in its original context;
2. identify whether the evidence shows it was intended as universal, shared-world, or instance-specific, without turning that interpretation into a Jim decision;
3. compare it with current project rules, including the universal principles in the project operating contract;
4. isolate contradictions, narrower restatements, and apparent scope changes;
5. preserve the recovered material and its provenance while applying Jim's existing disposition decisions; if a new consequential disposition is genuinely required, bring that choice to Jim rather than silently promoting, narrowing, discarding, or superseding the material.

A legacy rule that restates a current universal principle for one context is an application of the universal rule, not evidence that the principle is limited to that context. A legacy example illustrates only what its source establishes; it does not become an exhaustive boundary. Shorthand, analogies, archetypes, and influence references remain interpretive aids unless their underlying qualities or the reference itself were expressly established.

## Exact change scope

Every transformation or swap requires an explicit scope ledger. Define the target category and every affected field. Unlisted fields remain unchanged.

A description may mention an unchanged garment, object, habit, relationship, account, or setting for continuity. Mentioning it does not add it to the transformation. Descriptive completeness and change scope are separate.

If a cycle changes one category, do not treat a category heading as permission to change every example contained beneath it. Name the exact selected element or explicitly state that the whole category changes.

## Cumulative state

In a cumulative system, prior changes remain active until reversed under an established rule. “The footwear category has changed” does not necessarily mean the character must wear yesterday's exact shoes forever; it may mean future footwear selections come from the changed ownership or presentation pool. The instance ledger must distinguish:

- category ownership;
- current item worn or used;
- item location;
- permanent capability or rule;
- today's newly changed element.

Never reset prior changes at a new chapter, day, prompt, or scene.

## Boundary firewall

Separate physical, mental, social, perceptual, digital, legal, financial, relational, and historical effects. A mechanism affecting one layer does not automatically affect the others.

For digital effects, specify accounts, devices, identity fields, content history, messages, contacts, photographs, video, biometrics, professional systems, legal records, finances, calendars, and ongoing versus retroactive behavior separately.

For physical objects, specify ownership, location, dimensions, fitting, adaptive behavior, paired items, storage, and historical records separately. Do not alternate between adaptive resizing and fixed dimensions without recording a deliberate exception.

For mental effects, separate memory, information access, learned competence, muscle memory, preference, habit, personality, and identity. One does not imply the others.

## Controlled progression

When Jim defines a stopping point, stop there. Completing a transformation, dressing process, consultation, discovery, or technical sequence does not authorize travel, work, school, public reaction, a new day, or the next plot event.

Use a controlled pause after the requested unit. State remains active during the pause, but the characters do not enter suspended animation; the prose simply stops at a natural boundary and awaits direction.

## Natural narrative versus visible audits

Pre-generation checks can prevent drift, but they do not need to appear in finished prose. Maintain the ledger internally or in reference files. Include visible tables, status headers, or compliance blocks only when Jim requests that format or when the artifact itself is a technical record.

A complete outfit or environment should read as lived experience, not an inventory, unless item-by-item accounting is the point of the scene.

## Identity and naming

Once a character has a canonical name, use it rather than generic subject labels in prose. Names do not settle unresolved identity questions. Track separately anatomy, identity, presentation, pronouns, self-description, public perception, and what other characters know.

Do not force language to match anatomy when current canon establishes a different identity or social perception. Imported binary address tables do not override current identity and dignity rules.

## Verification instead of confirmation language

An assistant saying it has ingested, locked, updated, remembered, or completed a protocol proves nothing. Verify observable state:

- the controlling file exists;
- the new rule appears in it;
- the old rule is marked superseded or removed;
- dependent ledgers were updated;
- the next output follows the rule;
- the remote repository matches the local artifact.

Repeated failures in the recovered transcripts demonstrate that long prompt repetition alone does not guarantee compliance. Smaller modular references, explicit state fields, and post-write checks are more reliable.

## Contradiction patterns to test

Legacy systems commonly contained these incompatible defaults:

| Pattern | Required resolution |
|---|---|
| Total reality rewrite versus strict unchanged baseline | Define the precise affected layers and scope |
| Automatic item adaptation versus fixed original dimensions | Choose per mechanism or item |
| Granted competence versus no mental transfer | Define knowledge, skill, and muscle memory separately |
| Retroactive social history versus unchanged relationships | Define observer groups and relationship scope |
| Exhaustive description versus one-change limitation | Describe unchanged context without changing it |
| Automatic plot continuation versus user-directed pacing | Honor the explicit stopping point |

These are reusable diagnostic categories. The original story material remains only in `Systemwide/Source` and Historical Recovery; it is not part of this reusable system module.
