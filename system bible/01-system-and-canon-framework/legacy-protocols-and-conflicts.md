# Legacy Protocols and Conflicts

Status: RECOVERY EVIDENCE
Authority: NOT PROJECT-WIDE CANON

The sources below contain real design work and corrections, but they describe separate story engines or historical attempts. Their “absolute,” “system,” and “master” labels applied inside their original sessions and do not promote them over current canon.

## Cumulative life swap engine

`SYSTEM CORE INSTRUCTIONS.docx` and `SYSTEM CORE INSTRUCTION revised.docx` describe a husband-and-wife story in which one new aspect of life changes per day and prior changes accumulate permanently. The engine distinguishes physical devices from abstract digital footprints, requires named scope, tries to isolate unswapped domains, rewrites outside memories and records for selected swaps, and uses a state ledger to prevent reset.

The revised file generalizes some named examples into husband/wife placeholders and adds or intensifies execution gates. It is a revision, not a clean corrected specification. It contains unresolved contradictions:

| Issue | Clause A | Clause B | Disposition |
|---|---|---|---|
| Reality scope | Current holder's state is the only reality and origin is erased | Unnamed aspects remain exactly baseline with zero ripple | Requires an instance-level scope ledger; not globally harmonized |
| Object fitting | Magic relocates and adapts related items and dimensions | Anti-adjustment clause forbids resizing or recalibration | Direct internal conflict; unresolved in legacy engine |
| Skills and preferences | Swap grants skills, muscle memory, knowledge, and preferences | Strict isolation forbids implicit mental expansions | Must be specified per field; neither default is project-wide |
| Relationships | Outside reality retroactively treats state as always true | Relational firewall forbids rewriting unlisted bonds | Relationship scope must be explicit |
| Digital history | Threads, contacts, slang, and photos rewrite to current holder | Metadata, professional, legal, and financial domains stay anchored unless targeted | Useful scoped distinction, but exact boundary is instance-specific |
| Identity model | Reality conforms to the current holder | Faces, proper names, and continuing selves remain | Supports continuity of personhood only where explicitly retained |

The legacy rule requiring all messages to use binary slang based only on physical sex conflicts with current project governance, which separates anatomy, identity, presentation, self-description, and other people's knowledge. It remains evidence of that story engine, not a reusable identity rule.

## Cumulative Progression protocol transcripts

`Protocol-Ingestion-And-Subject-Query.docx` and `Protocol-Ingestion-and-Subject-Request.docx` are Gemini conversation exports, not clean protocols. They contain the initial Cumulative Progression Master Protocol, generated scenes, user corrections, assistant apologies, proposed rewrites, and repeated execution failures.

The underlying story mechanism uses a “Foreign Pilot” compulsion, biological adaptation, social-harmony perception, a daily target category, detailed grooming/dressing order, cumulative state, and a surface/body/motion/intellect taxonomy. It is a story-specific nonconsensual transformation framework, not project-wide canon.

The important decision chronology is:

1. The initial protocol directed automatic movement from the dressing ritual into work or school.
2. Jim explicitly changed this. Narrative must pause when dressing completes and wait for his direction.
3. Jim repeatedly clarified that only one designated subcategory changes in a cycle.
4. Previously changed categories remain part of the cumulative state, but the characters choose different items from their swapped category rather than literally wearing the same item every day.
5. All unchanged layers remain the character's own. The assistant repeatedly allowed unrelated swapped garments to “creep in”; Jim rejected that expansion.
6. A complete outfit description does not authorize extra swaps. Audit coverage and transformation scope are different things.
7. Names take precedence over anonymous labels once character names are established.
8. Assistant claims that the protocol was fully ingested did not prevent violations. Persistent state and explicit machine-checkable fields are more reliable than confirmation language.

The Query transcript includes an early younger character in a non-romantic transformation scenario. It cannot be generalized into romantic or sexual material. Current project rules require every character involved in attraction or intimacy to be unambiguously adult.

## Rigid presentation inversion world

`system principles.md` defines a separate rigid-binary setting in which men have male anatomy and mandatory extreme feminine presentation, women have female anatomy and mandatory extreme masculine presentation, neutral styling largely does not exist, and clothing, hair, cosmetics, nails, shoes, jewelry, accessories, uniforms, and props follow absolute inverted rules.

This is a potentially reusable world module, not universal Jim the Saga governance. Its mandatory styling conflicts with current project principles when applied globally, especially character agency, presentation not predetermining identity, and the rule that femininity or masculinity is not degradation. Preserve it for a story that explicitly invokes that world.

The file also contains a local inconsistency: it says accessories are “completely optional for men” and then requires men to wear earrings, necklaces, and bracelets. Purses are separately described as mandatory. This requires clarification before activation.
