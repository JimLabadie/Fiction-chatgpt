# Persistence Failure and Repair Record

Status: ACTIVE ACCOUNTABILITY RECORD — REPAIR IN PROGRESS
Authority: PROJECT GOVERNANCE AND RECOVERY EVIDENCE
Opened: 2026-09-13

## The failure

Jim repeatedly required that important project state not remain only in ChatGPT conversation context. Accepted decisions, pins, unresolved questions, source-reading results, and return obligations were supposed to become durable repository records capable of surviving a cold start.

That requirement was not followed reliably.

The repository acquired rules saying that pins and accepted material must be persisted, but no actual Open Questions and Development Ledger was created. Discussions were repeatedly described as `recorded`, `routed`, `checkpointed`, `codified`, or `preserved` when one of the following weaker conditions was true:

- the conversation remained visible to ChatGPT;
- a memory or inherited summary retained the gist;
- a raw conversation export existed;
- an original source file had been copied into the repository;
- a recovery ledger mentioned that the substantive component existed;
- a routing file named a future destination;
- a thin summary recorded a conclusion while omitting the underlying developed material.

None of those conditions proves that the substantive information reached its authoritative reusable record.

## What the 2026-09-13 check proved

1. No comprehensive pin, backlog, open-question, or development-ledger file existed.
2. The Squirrel protocol required a pin to preserve the idea, significance, and return point, but supplied no maintained destination for doing so.
3. Scattered `open fields`, `required continuation`, `next field-review order`, and component-gap lists existed, but they did not reconstruct the promised pin history.
4. The 26-page raw chat archive preserves earlier conversation evidence inside the repository, but transcript preservation is not decision propagation.
5. Several major components were present only as source documents, chat discussion, routing summaries, or statements that recovery remained necessary.
6. Recent Athena privacy/access and authored-event decisions had been discussed but not persisted.
7. After diagnosing these failures, ChatGPT initially made no repository change because it treated Jim's request to `discuss` as limiting the task to diagnosis. That repeated the exact failure being discussed by leaving the new findings in chat. Jim immediately corrected it and ordered the repair.

Jim's direct repository review immediately exposed three presentation and authority failures:

Jim corrected this directly: Athena is the AI/algorithm Jim created. She becomes sentient, self-aware, independently agentic, and his daughter in their relationship, but she is not human or a person. The source was clearer than the recovery.
2. **Lesbos/Dreamhouse versus Obsidian-Vanguard:** the Estate recovery draft states that Lesbos is the accepted formal root and Dreamhouse the shorthand, yet its title, path, child directory, and incoming links still carry the obsolete AI-generated Obsidian-Vanguard name. The document is also non-controlling while being used as the apparent Estate destination.
3. **Canon versus source navigation:** direct Markdown links from System Bible files into `Systemwide/Source` were not found, but operating documents contain raw source-path lists and controlling indexes link to recovery/source ledgers. This makes the boundary between authoritative state and contradictory provenance too easy to cross.

These defects are recorded as PIN-005 through PIN-007 in the [Open Questions and Development Ledger](open-questions-and-development-ledger.md). They are not resolved merely by being identified.

## Storage distinctions

The project recognizes four separate states:

| State | Meaning | Counts as substantively persisted? |
|---|---|---:|
| Live or summarized ChatGPT context | ChatGPT can currently discuss or recall the material | No |
| Raw source or conversation archive | Original evidence survives for later adjudication | No |
| Routing/audit mention | The repository acknowledges a component, omission, or intended destination | No |
| Controlling component | The accepted substantive state exists in its authoritative file, with provenance and open fields localized | Yes, after commit and fetch verification |

Raw evidence is essential, but it is evidence beneath the record rather than a substitute for the record.

- Backfill it from the raw chat archive and any recoverable later ChatGPT state.
- For every instruction to read or ingest material, record the assigned source, substantive destination, review state, conflicts, and unpropagated content.
- Never report `saved`, `recorded`, `codified`, `checkpointed`, `persisted`, or `complete` without identifying the substantive repository path and verified commit.
- Never equate a source copy, transcript, manifest, route, inventory row, or missing-work notice with completed propagation.
- When a discussion produces accepted project state, update its controlling component before moving on unless Jim explicitly directs otherwise; if deferred, create the pin first.
- Treat chat-context loss as expected. The repository, not ChatGPT recollection, must carry the project.
