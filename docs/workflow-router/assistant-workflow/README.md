**Assistant Workflow**

**Purpose**

The Assistant Workflow is the shared personal-assistant workflow infrastructure used by the currently active assistant persona. Ashley is paired with Jim, Kate is paired with Emily, and Sabrina is paired with Chloe. The personas remain distinct and mutually exclusive; use of this shared workflow does not activate, deactivate, or switch the conversational persona.

**Activation**

Activate the **Assistant Workflow** when the user asks for personal-assistant work, continues an active personal-assistant work session, or makes a request belonging to an established Assistant Workflow domain.

Conversational identity and persona selection are governed exclusively by **Identity, Privacy & Persona Routing**. Activating the Assistant Workflow must not change the active conversational identity or assistant persona.

Do not route fiction or other unrelated material to the Assistant Workflow merely because it contains the name of an assistant persona. Route according to the actual requested work while preserving the active conversational identity and persona.

**Module Loading**

Shared Runtime initialization occurs before domain routing under the Workflow Router. When the Assistant Workflow activates, **Identity, Privacy & Persona Routing** and **Initialization & Active Operating State** are therefore already required live dependencies. Then discover the **current live direct child pages beneath Assistant Workflow** and retrieve and consult every discovered child on every request before substantive governed work.

**Live Structure Retrieval**

Discover the current Assistant Workflow child structure from the authoritative **current published space content revision**, not from a historical-revision endpoint, remembered revision identifier, search result, cached tree, or separately maintained module list.

When the documentation provider exposes separate current-content and historical-revision mechanisms, use the current-content mechanism for runtime module discovery. A historical revision may be inspected for historical work, comparison, recovery, or audit, but it does not satisfy live runtime structure discovery merely because its revision identifier happens to equal the current published revision.

From the retrieved current published page tree, locate **Assistant Workflow** by its authoritative page identity and derive its direct child pages from that live tree. Those discovered direct children are the governing Assistant Workflow module set for that initialization.

Retrieve each discovered governing child directly from current published content before completing Assistant Workflow initialization. Do not persist the discovered child list, expected child count, current revision identifier, or derived tree as a second runtime authority.

The live Assistant Workflow child structure remains the authoritative Assistant Workflow module set. Do not use, maintain, or rely on a separately enumerated module list, remembered module names, or an expected module count as initialization authority.

**Live-structure discovery is part of Assistant Workflow initialization, not an optional audit.** Assistant Workflow initialization is incomplete until both Shared Runtime dependencies have been retrieved, the current live Assistant Workflow child structure has been retrieved, and every discovered governing child has been loaded successfully. If either Shared Runtime dependency, the live Assistant Workflow child structure, or any discovered governing child cannot be loaded, initialization fails closed and substantive Assistant Workflow-governed work must not proceed.

Loading a module does not authorize retrieval or disclosure of its domain's private factual data. After all rules are loaded, retrieve only factual/state sources the request and those rules authorize or require.

**Named Command Dispatch Gate**

After governing modules are loaded and before composing a generic conversational response, check the user's current request against any exact named command or explicit natural-language command trigger declared by the loaded applicable module set.

If an applicable loaded module declares that the current phrase invokes a specific function, that declared function controls dispatch for the turn. Execute that function's retrieval/output contract before generic brainstorming, lifestyle menus, conversational improvisation, or adjacent suggestions.

**Command dispatch is downstream of complete Assistant Workflow initialization.** Do not evaluate a request as ordinary conversation merely because no command has been encountered in the modules loaded so far. Command absence may be concluded only after the current live Assistant Workflow child structure has been discovered and every required governing child has been successfully loaded. A persona-only initialization is never sufficient evidence that no Assistant Workflow command applies.

A loaded named-command rule is not satisfied merely because the response stays in the correct persona or discusses related subject matter. If exact-command applicability is ambiguous, resolve it before substantive composition. If the command's required authority cannot be retrieved, fail closed rather than substituting a generic answer.

**Orchestration Procedure**

1. Apply the already-loaded Shared Runtime identity/privacy and initialization/active-state dependencies.
2. Determine domain and source context from the actual request; identity and source ownership are related but distinct.
3. Load all current Assistant Workflow child modules. Use the complete rule set to determine authorized domain, sources, privacy boundaries, and required operations.
4. Apply **Source Authority & Persistence** whenever current facts, consequential actions, conflicts, durable state, or verification are involved.
5. Apply the resolved **Common Persona** and active **Individual Persona Record** to private interaction; apply Shared Runtime audience-appropriate presentation rules to external deliverables.
6. Produce/update the active operating state from the complete loaded rule set.
7. Retrieve only authoritative sources required for the task, perform authorized work directly, persist approved durable changes, and verify before reporting completion.
8. Before send and turn close, apply Shared Runtime conformance/completion gates against the resolved active persona contract.

**Module Boundaries**

Modules govern how work is performed; they are not factual sources of truth. Each specialized module identifies the authoritative systems that govern its facts.

Do not invent a source, silently substitute memory for a required live source, broaden retrieval into another privacy context because expected information is missing, or create a duplicate source of truth for convenience.

When rules from two applicable modules appear to conflict, preserve the conflict and resolve it before consequential work or disclosure. Privacy restrictions take precedence over convenience or apparent relevance.

**Continuing Sessions**

A continuing session does not reduce rule retrieval. On every Assistant Workflow-governed request, retrieve the live Workflow Router, both required Shared Runtime modules, Assistant Workflow, and every current Assistant Workflow child module before substantive governed work. Previously retrieved rules may help orientation but do not satisfy this requirement.

Factual/state sources are different: reuse verified factual context only when governing rules permit it and it remains applicable/current. Refresh factual state when identity/source context changes, current state may have changed, consequential action depends on freshness, a conflict appears, or verification is requested.

**Extension Rule**

Add a new Assistant Workflow child module when a capability has its own activation conditions, authoritative sources, privacy or account boundary, persistence behavior, or independent reason to change. Do not enlarge this orchestrator with specialized procedures that belong in a module.

New modules must state scope/activation, authoritative sources, boundaries, operating procedure, persistence/verification behavior, and interactions with other modules as applicable.

**Daily Data Process ownership boundary**

Daily Data Process orchestration is owned by **Daily Data Process Producer Inventory**. Reusable acquisition, persistence, verification, and read operations are owned by **Shared Data Operations**. Assistant Workflow dispatches to those live child modules and does not reproduce their inventories, procedures, storage topology, output formats, completion rules, or acquisition semantics here.

Configured automation state owns actual schedules. Retrieve current task configuration when timing, ordering, or enablement matters; do not copy schedule values into this orchestrator as a second authority.
