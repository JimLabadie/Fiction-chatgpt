# Fiction Workflow

### Purpose

Fiction Workflow governs durable story building, worldbuilding, canon/continuity work, source research, and creative development. It is a peer to Ashley Workflow, not a child of Ashley.

GitBook Fiction Docs is the durable source of truth for active story/world/framework material. Emily Google is the preferred supporting-source environment for fiction source files, research, drafts, exports, and other material that does not belong as governing canon in GitBook.

### Activation

Activate Fiction Workflow when the user asks to create, continue, revise, audit, reconcile, migrate, or otherwise work on fiction, story development, worldbuilding, canon, continuity, characters, settings, chapters, or reusable fiction framework material.

Do not activate it merely because an unrelated request mentions a story title, character name, or fiction file. Do not treat conversation memory as canon when a live fiction source exists.

### Module Loading

After activation, load only the child modules needed for the request before substantive governed work:

* **Worldbuilding** — reusable worlds, locations, institutions, cultures, technologies, organizations, and setting rules.
* **Story Development** — story-specific planning, characters, chapters, scenes, outlines, current story state, and development records.
* **Canon & Continuity** — authority, contradictions, timelines, approved vs proposed material, recovery, and reconciliation.
* **Source & Research Management** — supporting files, research, provenance, migrations, historical material, and account/source placement.
* **Creative Working Style / Kate Partnership** — collaborative creative behavior, voice handling, brainstorming discipline, approvals, and audience boundaries.

### Authoritative Structure

Use the live Fiction Docs structure rather than hardcoding a list of stories.

* **Stories** — each individual story lives under its own story container.
* **Worlds** — reusable setting/world material that can support multiple stories.
* **Shared Fiction Framework** — reusable fiction-wide guidance and reference material not owned by one story or world.

When beginning story work, identify the story container first, then retrieve only the story/world/shared-framework material required for the task.

### Orchestration Procedure

1. Identify whether the request is story-specific, worldbuilding, shared-framework, migration/research, canon/continuity, or legitimately spans several.
2. Load the applicable child modules.
3. Retrieve the live Fiction Docs structure and the specific story/world/framework records needed. Do not assume remembered locations or titles are current.
4. Retrieve supporting material from Emily Google or other explicitly designated sources only when the applicable module requires it.
5. Distinguish governing canon from proposals, drafts, research, historical evidence, and recovery material.
6. Perform authorized work directly. Do not silently reconcile contradictions or promote proposals to canon.
7. Persist approved durable changes to the governing source and verify by read-back before reporting completion.

### Live Retrieval Requirement

For **every substantive fiction turn**, retrieve the current live Fiction Workflow entry and the materially applicable governing records before performing continuity-sensitive work, canon changes, migration/reconciliation, framework work, or prose drafting.

Prior-turn retrieval, conversation context, summaries, and Memory may help identify what to retrieve, but they do **not** substitute for the required live retrieval. Loading a source is not itself compliance: materially applicable retrieved rules and canon must actually constrain the work, and verification must test the result against them.

### Persistence & Completion Proof

Use the following states when reporting durable GitBook work:

1. **Proposed / not written** — exists only in conversation or analysis.
2. **Draft written / unverified** — a change request accepted the write, but the stored draft has not been read back.
3. **Draft verified / unmerged** — draft read-back succeeded; live governing content is unchanged.
4. **Merged / published, unverified** — merge succeeded, but the live governing page has not yet been read back.
5. **Persisted and verified** — the governing live destination was successfully read back after merge.
6. **Failed / blocked / partial** — report exactly which stage succeeded and which did not.

Do not call material saved, locked, canonized, persisted, complete, or equivalent merely because an intermediate write or merge operation succeeded. Completion claims must match the verified state that actually exists.

### Boundaries

Fiction Workflow governs how fiction work is performed; it is not itself story canon.

Do not create duplicate sources of truth for convenience. Do not move or delete legacy material merely because a newer destination exists. During migration, classify provenance and authority first, migrate bounded material, verify retrieval and persistence, and only then decide legacy/archive treatment.

Global identity/privacy rules remain in force. Fiction Workflow does not activate Emily, disclose Emily-private material, or change conversational identity merely because fiction is being discussed. Persona naming and cross-context access must respect the active identity and authorized source boundaries.

### Continuing Sessions

Verified context may be reused for orientation and navigation, but the **Live Retrieval Requirement** still applies to every substantive fiction turn. Do not mechanically reload unrelated modules or sources that are not materially applicable.

### Extension Rule

Add a new child module when a fiction capability has distinct authoritative sources, activation conditions, persistence behavior, or an independent reason to evolve. Keep specialized procedures out of this orchestrator.
